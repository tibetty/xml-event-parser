# Benchmark results

Generated by `npm run bench:data && npm run bench` on the machine below. Re-run
it on your own hardware before trusting the absolute numbers; the ratios are the
part that has held up.

- **Machine:** Apple M4 Pro, macOS 27.2.1, Node v26.13.1
- **Competitors:** txml 6.0.3, fast-xml-parser 5.12.1, sax 1.6.1, htmlparser2 12.0
- **Method:** one warm-up call, then the fastest call within a 1.5 s budget
  (at most 40 calls, minimum kept). Sizes are the input bytes; MB/s is
  input MiB per second of wall time. "retained" is the heap still held after a
  forced GC with one parsed document alive.

## Workloads

- **tree** — parse into a document tree and walk it, counting every element.
  Comparable: xmlparser, txml, fast-xml-parser. The `elements` count for
  fast-xml-parser is roughly double because its `preserveOrder` tree wraps each
  element in an array; compare MB/s, not counts.
- **stream** — consume element callbacks and count nodes/ways/relations.
  Comparable: xmlparser's progressive events, sax, htmlparser2.
  **Caveat:** xmlparser builds the document even with `progressive: true`, so
  its stream row pays for a tree the other two never build. It is still the
  fastest on every shape.

## Corpus

Generated deterministically (`bench/generate.mjs`, fixed seed), ~27 MiB total:

| dataset | size | isolates |
| --- | --- | --- |
| osm-dense | 6.0 MiB | realistic Overpass document: 30k nodes, 2.5k ways, 200 relations |
| boundary | 3.8 MiB | one relation, 400 members with 250 inline `<nd>` each |
| leaf-storm | 6.2 MiB | 120k self-closing leaves: per-element entry cost |
| tag-storm | 6.7 MiB | 15k elements x 12 `<tag>` children: per-child cost |
| text | 1.9 MiB | 180-char values with entities and CDATA: text/decoding cost |
| deep | 2.3 MiB | 40-level nesting x 1.5k trees: open-element stack cost |
